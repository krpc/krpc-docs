# Native client languages

**Status:** proposal. No GitHub issue yet.

## Goal

Choose which languages get an official native client next. An official client lives in `krpc`, is
generated by clientgen, passes the conformance suite, and has a tab on every API reference page.

gRPC (KSA, and KSP through the adapter) is an interop layer. A gRPC stub lacks streams, events,
nullable handling and the other client spec features. It does not stand in for a native client in a
popular language.

## Current coverage

| Client | Also covers |
| --- | --- |
| Python | |
| C# (.NET Standard 2.0) | F#, VB, PowerShell |
| Java | Kotlin, Scala, Clojure, MATLAB (runs a JVM) |
| C++, C-nano | Languages with C interop: Zig, Nim, D, Swift, Julia |
| Lua | |
| JavaScript/TypeScript ([in progress](javascript-client.md)) | Browser and Node.js |

The gap is popular languages with their own ecosystems and awkward FFI, where users expect a native
library: **Rust** and **Go**.

## Recommendation

| Order | Language | Reason |
| --- | --- | --- |
| 1 | JavaScript/TypeScript | Already in progress, see [javascript-client.md](javascript-client.md) |
| 2 | Rust | Most active third-party demand: three clients, one maintained |
| 3 | Go | Channels map onto streams and events; one stale third-party client |

Not recommended:

| Language | Reason |
| --- | --- |
| Kotlin | Uses the Java client. A thin idiomatic wrapper (coroutines, nullable types) could come later |
| Ruby | Declining; Python serves the same scripting audience |
| Swift, Haskell, Julia | Audience too small for the per-client cost |
| MATLAB / Simulink | A docs page on calling the Java client from MATLAB is cheaper than a client |

### Rust

- Protobuf through `prost`. Nullable values are `Option`, errors are `Result`.
- Blocking API by default; an async API behind a cargo feature, so a simple script does not pull in
  tokio.
- Streams and events as channels or callbacks.
- Bazel: `rules_rust` with `crate_universe`.
- Published to crates.io.

**Prior art changes the plan.** [kladd/krpc-client](https://github.com/kladd/krpc-client) is
maintained: it tracks server v0.7.0 (October 2026) and has the most downloads of the Rust crates.
Before writing a new client, ask its author about the official client, as was done with krpc-node
for [JavaScript](javascript-client.md#prior-art). Possible outcomes: the official client builds on
it, the author maintains it inside `krpc`, or it is blessed on the third-party page and we build our
own. Its GPL-3.0 license matters for the first two; see [relicense-mit.md](relicense-mit.md).

**Crate name.** crates.io has no namespaces, and the obvious names are taken:

| Crate | Owner | State |
| --- | --- | --- |
| `krpc` | unrelated project | An unrelated tokio RPC library |
| `krpc-rs` | krpc-rs org | kRPC types, last release 2017 |
| `krpc-client` | kladd | Maintained third-party client |

`krpc-org` (matching the npm org `@krpc-org`) and `ksp-krpc` were free on 2026-11-05. crates.io's
usage policy forbids name squatting, so the name is published with the first real release.

### Go

- Goroutines and channels for streams and events; generics for a typed `Stream[T]`.
- Bazel: `rules_go`.
- No registry. The module path is the repository path, versioned by git tags. A module in
  `client/go` needs tags like `client/go/v0.8.0`, beside the `ksp-v*` and `clients-v*` release tags.
  Settle this, or a separate repo, before the first release.

## Cost per client

- A clientgen backend and a docgen target.
- A conformance testee, with its `expected-failures.txt` and `unsupported.txt`.
- A CI job and a package publish step.
- A tab on every API reference page, and compiled examples in `doc/src/scripts/` for every page that
  has them. This is the largest ongoing cost, and the reason to stop at two new languages.
